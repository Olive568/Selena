FIX #2: Make transfers atomic
------------------------------------------------------------
Root Cause: transaction-manager.tsx:393-437 and
transactions-page.tsx:416-461 issue two INSERTs (transfers table +
transactions table) in separate statements. If the second fails,
a transfer record exists with no matching transaction.

Files Created:
  - supabase/migrations/20260729_atomic_transfer.sql
    - Creates create_transfer RPC function that inserts both
      transfer and transaction records in a single atomic
      database transaction (plpgsql block)

Files Modified:
  - components/transaction-manager.tsx
    - Lines 393-437: Replaced dual-insert block with single
      supabase.rpc("create_transfer", {...}) call

  - components/transactions-page.tsx
    - Lines 416-461: Replaced dual-insert block with single
      supabase.rpc("create_transfer", {...}) call

Solution:
  A PostgreSQL function (security definer) wraps both INSERTs
  in a single transaction. The function validates amount > 0.
  Client code now calls supabase.rpc("create_transfer", {...})
  instead of two sequential supabase.from(...).insert() calls.
  If either insert fails, both roll back.

FIX #3: Add idempotency on all writes
------------------------------------------------------------
Root Cause: No idempotency key existed. Client-side isSubmitting
was bypassable. Network retry or double-click could create
duplicate transactions, transfers, categories, or accounts.

Files Created:
  - supabase/migrations/20260729_idempotency.sql
    - Added idempotency_key text UNIQUE column to transactions,
      transfers, categories, and accounts tables

Files Modified:
  - supabase/migrations/20260729_atomic_transfer.sql
    - Updated create_transfer RPC to accept p_idempotency_key
      parameter and use ON CONFLICT (idempotency_key) DO NOTHING.
      If the transfer insert is a duplicate, the function returns
      early without inserting the transaction.

  - components/transaction-manager.tsx
    - Transfer RPC call: Added p_idempotency_key: crypto.randomUUID()
    - Category insert: Added idempotency_key, handles 23505 error
      by fetching existing record via key
    - Account insert: Added idempotency_key, handles 23505 error
      by fetching existing record via key
    - Transaction insert: Added idempotency_key to non-editor insert,
      handles 23505 error by silently returning (idempotent)

  - components/transactions-page.tsx
    - Same four changes as transaction-manager.tsx

  - components/new-user-onboarding.tsx
    - Bulk transaction insert: Added unique idempotency_key per row
      (crypto.randomUUID() per entry), handles 23505 error silently

  - lib/__tests__/finance.test.ts
    - Fixed TypeScript type inference issue in balance computation
      test (added explicit type annotation for transactions array)

Solution:
  Every insert now generates a unique idempotency_key via
  crypto.randomUUID() and includes it in the payload. The database
  has a UNIQUE constraint on idempotency_key. On duplicate key
  violation (PostgreSQL code 23505), the operation is treated as
  idempotent — transfers are skipped via ON CONFLICT DO NOTHING,
  transactions silently return, and categories/accounts fetch the
  existing record. This prevents duplicates from network retry or
  double-clicks.

FIX #9: Add server-side validation for all money writes
------------------------------------------------------------
Root Cause: All mutations went directly from browser to Supabase
via the anon key. No server-side validation existed for amounts
or transaction types. The database had no CHECK constraints and
client code had direct INSERT/UPDATE/DELETE access to tables.

Files Created:

  - supabase/migrations/20260729_server_validation.sql
    - DB CHECK constraints:
      * transactions.amount > 0 (positive amount)
      * transfers.amount > 0 (positive amount)
      * transactions.amount < 1e12 (finite amount cap)
      * transaction_type IN ('income','expense','transfer')
    - 6 new RPC functions (all security definer):
      * create_transaction(p_user_id, p_merchant, p_amount, p_date,
        p_notes, p_transaction_type, p_category, p_payment_method,
        p_account_id, p_idempotency_key) — validates amount > 0 and
        valid transaction type, handles idempotency
      * update_transaction(p_id, p_user_id, ...) — partial update
        with same validations, returns updated row as JSONB
      * delete_transaction(p_id, p_user_id) — deletes only if
        user_id matches, raises exception if not found
      * create_category(p_user_id, p_name, p_idempotency_key) —
        validates name non-empty and <= 100 chars
      * create_account(p_user_id, p_name, p_idempotency_key) —
        same validation as categories

Files Modified:

  - components/transaction-manager.tsx
    - createCategoryRecord: replaced direct table insert with
      create_category RPC
    - createAccountRecord: replaced direct table insert with
      create_account RPC
    - handleSaveTransaction (else/insert): replaced direct insert
      with create_transaction RPC
    - handleSaveTransaction (if/update): replaced direct update
      with update_transaction RPC
    - handleDeleteTransaction: replaced direct delete with
      delete_transaction RPC

  - components/transactions-page.tsx
    - Same five replacements as transaction-manager.tsx

Solution:
  Two-layer server-side validation: (1) CHECK constraints at the
  database level enforce amount > 0, finite amounts, and valid
  transaction types regardless of how data reaches the DB. (2) RPC
  functions with explicit parameter validation replace direct table
  access, allowing the browser anon key to be restricted to only
  EXECUTE on these validated RPCs (requires RLS policy change in
  Supabase dashboard to revoke direct table INSERT/UPDATE/DELETE).

FIX #10: Fix floating-point accumulation in all money math
------------------------------------------------------------
Root Cause: Number() in JS is IEEE-754 double precision. Financial
calculations like 0.1 + 0.2 produce 0.30000000000000004. All
balance/metric calculations accumulated via JS number addition,
introducing rounding errors over time.

Files Created:

  - supabase/migrations/20260729_integer_cents.sql
    - Converts transactions.amount from numeric to bigint (cents)
    - Converts transfers.amount from numeric to bigint (cents)
    - Adds positive amount and finite amount CHECK constraints
    - Recreates all RPCs (create_transfer, create_transaction,
      update_transaction) with p_amount bigint instead of numeric

Files Modified:

  - lib/finance.ts
    - normalizeTransaction: divides amount by 100 when reading
      (amount / 100) to convert DB cents to display units

  - components/transaction-manager.tsx
    - Added amountInCents = Math.round(values.amount * 100) after
      validation
    - All RPC calls use amountInCents instead of values.amount

  - components/transactions-page.tsx
    - Same changes as transaction-manager.tsx

  - components/new-user-onboarding.tsx
    - Changed amount: Number(value) to
      Math.round(Number(value) * 100) for cent conversion

  - lib/__tests__/finance.test.ts
    - normalizeTransaction "parses string amount" test: input
      changed from "123.45" to 12345 (cents), expected output
      remains 123.45 (display units)
    - Balance computation tests: all monetary values multiplied
      by 100 to represent cents, expectations updated accordingly

Solution:
  Database stores all monetary values as integer cents (bigint),
  eliminating floating-point errors. Client-side form input is
  converted to cents via Math.round(amount * 100) before writing.
  On read, normalizeTransaction divides by 100 to restore display
  units. All calculations on display units still use Number but
  only for presentation; the source of truth (cents) is always an
  exact integer. formatCurrency continues to work as it receives
  display-unit values.
